# M6 explainer: one-page situation report and map dashboard

Brief, "OUTPUT": *"A map dashboard, plus a one-page situation report generated by the
system."* Judging: *"Dashboard and situation report usability: 10 %"*. Each part below covers
what, why, what if removed, and what could replace it.

---

## 1. One-page situation report (`floodmap/sitrep.py`, stage `report`)
- **What:** an A4 page (PDF + PNG) and a plain-text version (for radio/SMS relay), in every
  run's `report/` folder. Rebuild for any existing run with `python -m floodmap report
  [--run outputs/<id>]`.
- **Contents, top to bottom:**
  1. **Title band:** "EDUCATIONAL PROTOTYPE — NOT AN OPERATIONAL TOOL" (responsibility
     note).
  2. **Event, flood date, area, bounding box, generation time, run id:** traceable to its
     results.json.
  3. **Key figures (estimates):**
     - area potentially affected, by confidence;
     - buildings potentially affected;
     - motorable road in flood/debris;
     - bridges;
     - health facilities;
     - settlements likely cut off (and their buildings), with no footpath either, and
       likely lost access to every hospital.
  4. **Map:** the cut-off map's focus window, or the best available map.
  5. **Rescue priorities** (top 7, with their reasons).
  6. **Key road and bridge breaks** (which break cuts off the most buildings).
  7. **Flood path:** low-lying settlements along it.
  8. **AI model:** new water and test score, labelled "second opinion".
  9. **Limitations:** includes the brief's own example (revisit time) and "verify on the
     ground".
  10. **Footer:** the required attributions, verbatim from `floodmap.attribution`, the
      prototype disclaimer, and the Sen1Floods11 citation when the model ran.
- **Why a template, no language model:**
  - The author decided on no external AI.
  - It also guarantees *every number comes from results.json*: the report receives exactly
    the dictionary written to results.json and nothing else.
  - A stage that did not run appears as "not available (<reason>)", never as an invented
    number or a crash.
- **Why matplotlib for the PDF:** it is already a dependency, works offline on every OS, and
  needs no browser or extra font packages.
- **Local-script names:** settlement names in Devanagari would show as empty boxes in the
  PDF font, so they are replaced by coordinates ("settlement at 28.123N 85.312E"). The
  dashboard tables show the original names.
- **If removed:** a required deliverable is missing.

## 2. Map dashboard (`app/streamlit_app.py`, `python -m floodmap dashboard`)
- **What:** a local web app.
- **Sidebar, "New analysis":**
  - pick a prepared event, or type a bounding box + flood date + name;
  - optionally an upstream point for the flood-path bonus;
  - press *Run analysis*, which shows live progress from every stage.
- **Sidebar, "Open a previous run":** browse earlier results without recomputing.
- **Main view:**
  - prototype banner and four headline numbers;
  - the status of every processing stage;
  - tabs for the brief's questions: *Situation report* (with PDF/PNG/text downloads),
    *Where did the flood hit?*, *What was damaged?*, *Who is cut off?*, *Rescue
    priorities* (CSV download), *Flood path (bonus)*, *AI model*, *Data & limitations*;
  - GeoJSON downloads (OSM-derived files carry the ODbL licence);
  - the required attributions as the footer of every page.
- **Why Streamlit (author approved 2026-10-13):** pure Python, runs locally, and calls the
  same `run_pipeline` as the CLI and the tests. The dashboard never computes its own
  numbers.
- **Security and privacy** (`.streamlit/config.toml`, enforced by `tests/test_dashboard.py`):
  - `gatherUsageStats = false`: Streamlit would otherwise send usage statistics. Author
    rule: nothing leaves the machine.
  - `address = "localhost"`: other computers on the network cannot open it.
  - `showErrorDetails = "none"`: no tracebacks or file paths in the browser; details go to
    the redacted log.
  - `fileWatcherType = "none"`: the app does not reload itself during a live demo.
  - Inputs are validated by the pipeline (bounding box, size limits). Input errors show a
    clear message, never a traceback.
- **Maps are our own images:** Copernicus DEM hillshade with our layers. No external map
  tiles are used, because they would contain current (post-event) OSM and an outside
  connection.
- **Alternatives considered:**
  - an interactive web map (Leaflet/folium): loads JavaScript and tiles from the internet;
  - a custom web server: more code to secure.

## 3. Tests
- **Privacy settings test:** fails if usage statistics, network exposure or error details
  are ever switched on.
- **Headless render with Streamlit's test harness:** (1) no runs yet → helpful message, no
  error; (2) a run where some stages failed → the app shows "Not available: <reason>", the
  headline numbers that exist, and does not crash.
- **In-app browser check (2026-10-13):**
  - the Trishuli run renders with every tab and its maps and tables, and no console errors;
  - a *new analysis started from the dashboard* runs live with progress messages
    (section 4);
  - a deprecated Streamlit argument flagged in the server log was replaced.
