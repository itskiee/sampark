# M0 explainer — project setup, data-rule guard, security, CI

For every part: **what it is**, **why we did it**, **what happens if you remove it**, and
**what could replace it**. The "Judge may ask" lines are practice for Q&A.

---

## 1. Python environment and dependencies

### `.venv` (virtual environment)
- **What:** a private Python installation inside the project folder.
- **Why:** project packages (rasterio, openeo, ...) don't mix with other Python
  projects on the machine, and anyone can recreate exactly the same environment.
- **If removed:** packages go into the system Python; version clashes with other projects;
  "works on my machine" problems for judges.
- **Alternatives:** conda (good for geospatial, but heavier and a second tool for judges),
  Docker (most reproducible, but slow to build and heavy for a live demo). We chose venv +
  pip because every package we need ships ready-made wheels for Windows/Linux/macOS.

### `pyproject.toml`
- **What:** the project's definition: package name `floodmap`, dependency list, settings for
  pytest and ruff.
- **Why:** turning the code into an installable package (`pip install -e .`) means the CLI,
  the dashboard and the tests all import the *same* `floodmap.pipeline.run_pipeline`.
  No copy-pasted logic that can drift apart.
- **If removed:** we'd need `sys.path` hacks; tests might test different code than the app runs.
- **Alternative:** `setup.py` (older style), Poetry (another tool to install).

### `requirements.txt` / `requirements-dev.txt` with hashes
- **What:** every package pinned to an exact version **plus a SHA-256 fingerprint** of each
  allowed file. Generated by `uv pip compile --universal --generate-hashes` from the loose
  list in `pyproject.toml`.
- **Why:**
  1. *Reproducibility:* judges install exactly what we tested.
  2. *Supply-chain integrity:* `pip install --require-hashes` refuses any file whose hash
     doesn't match. A tampered or swapped package cannot be installed silently.
  3. `--universal` makes one file valid on all OSes and Python 3.11–3.13. That's why some
     packages appear twice with markers (e.g. numpy 2.4.6 for 3.11, 2.5.3 for 3.12+, because
     numpy 2.5 dropped 3.11).
- **If removed (unpinned):** a new release of any of ~70 transitive packages could break
  the demo overnight.
- **Alternative:** `pip freeze` (pins versions but no hashes, and only for one OS),
  pip-tools (similar; uv is faster and handles cross-platform markers).
- *Judge may ask:* "How do you know the code the judges install is what you tested?"
  → Hash-locked requirements, the same file in CI on Windows and Linux.

## 2. Configuration (`configs/default.yaml`, `config.py`)
- **What:** all tunable numbers live in one commented YAML file. Events (like Trishuli)
  are separate small files in `configs/events/`. pydantic validates everything at load.
- **Why:**
  - *Nothing Trishuli-specific in code.* A judge's new area is just new input.
  - *Defensible numbers:* each value has a comment explaining why it was chosen.
  - `extra="forbid"`: a typo such as `max_aoi_kmm2` is an **error**, not a silently ignored
    setting. Silent typos are a classic way demos break.
  - The models have **no defaults of their own**, so the YAML is the single source of truth
    (code and YAML cannot disagree).
- **If removed:** magic numbers scattered in code; changing a threshold means editing code.
- **Alternatives:** hydra / dynaconf (more features, more dependencies); environment
  variables (not suitable for dozens of numeric settings).
- **Secrets are deliberately NOT config:** they come only from `.env`/environment and are
  held as `SecretStr` (prints as `**********`).

## 3. Area of interest (`aoi.py`)
- **What:** turns a bbox, GeoJSON (Polygon/Feature/FeatureCollection), GeoJSON file or
  shapely geometry into a validated AOI with geodesic area, UTM zone and a stable hash.
- **Why:** judges type arbitrary inputs live. Every bad input (inverted box, wrong order,
  point instead of polygon, broken file, area too big/small, self-intersecting polygon)
  becomes a clear `AOIError` message instead of a crash deep in the satellite processing.
  - *Geodesic area* (on the WGS84 ellipsoid) is correct at any latitude; naive degree math
    is wrong by a factor of cos(latitude).
  - *UTM zone:* rasters are processed in metres with square pixels, so areas, distances and
    road lengths later are simple arithmetic. Trishuli → EPSG:32645 (zone 45N).
  - *Stable hash* (normalised, rounded to ~0.1 m): the same area always maps to the same cache
    entry regardless of vertex order.
  - *Area cap* (2,500 km²): bounds download time so a live run cannot hang.
- **If removed:** a typo in a judge's input crashes the run during judging, which is the
  worst outcome per the brief's live evaluation.

## 4. Results and stage statuses (`results.py`, `pipeline.py`)
- **What:** `run_pipeline()` is the single entry point. Each stage returns a `StageResult`
  with status `ok | partial | skipped | failed`, a human message, outputs, warnings and timing.
- **Why (robustness):**
  - Each stage runs in its own try/except, so one failure (e.g. "no cloud-free Sentinel-2")
    never takes down the whole run. The rest continues with what it has.
  - A stage whose inputs are missing is **skipped with the reason**, not crashed.
  - Failed stages get an **error id**; the full traceback goes only to the local log, and
    the user sees a short message. Keeps internals and any secrets off the screen.
  - `results.json` is **always** written (even after failures). It's also the only source of
    numbers the copilot may use (M5), which is how we meet "every number must come from your
    system's maps".
  - Only **relative paths** are written (no `C:\Users\<name>\...`): privacy (tested).
- **If removed:** any exception anywhere = crash in front of judges.
- **Alternative:** workflow engines (Prefect, Airflow, Snakemake): powerful but heavy for a
  live single-user demo.

## 5. Cache (`cache.py`)
- **What:** `cache/<aoi_hash>_<date>/<stage>_<settings-hash>/` folders.
- **Why:**
  - Re-runs and the live demo are fast (Copernicus Data Space processing can take minutes).
  - The key includes the stage's **settings and the pipeline version**. If we change a
    threshold, the old result is not reused (approved proposal P7). Keying only on AOI + date
    would show stale maps after tuning.
  - A folder only counts once a `_COMPLETE` marker is written **last**. A crash halfway
    through a download leaves no marker, so the half-file is discarded, never used.
- **If removed:** every run re-downloads everything (slow demos); without the marker a
  truncated file could produce a corrupt map.

## 6. Data-rule guard (`data_rules.py` + `tests/test_data_rules.py`)
Breaking the data rules = disqualification, so they're enforced three ways:

1. **Runtime allowlist** (`data_rules.py`): data collections can only be opened through
   `cdse_client.load_collection()`, which accepts only `SENTINEL1_GRD`, `SENTINEL2_L2A`,
   `COPERNICUS_30` (Copernicus DEM). Catalogue searches only `sentinel-1-grd` /
   `sentinel-2-l2a`. Our HTTP only to `api.ohsome.org` and `stac.dataspace.copernicus.eu`
   (LLM host added in M5); the openEO client only ever gets the CDSE endpoint constant.
   Anything else raises `DataRuleViolation`.
2. **Static scanner** (`tests/rules_scanner.py`): parses all code in `src/ app/ scripts/`
   with Python's `ast` module and fails on: imports or paths to `validation/`; osmnx or its
   download functions; Overpass; identifiers of forbidden datasets (JRC water, WorldCover,
   WorldPop, MERIT, other DEMs, building-footprint products, EMSR...); **Earth Engine /
   geemap imports or the openEO federation endpoint**; `load_collection()` with a collection
   outside the allowlist; HTTP libraries outside `net.py`; unreviewed URLs.
3. **Scanner self-tests:** 30 planted violations, each of which must be caught. A scanner
   that silently stops working would otherwise pass forever.

- **Why the denylist lives in tests/, not src/:** the pipeline code then contains no forbidden
  dataset names at all, not even in a "forbidden" list.
- **OSM snapshot rule:** `ohsome_snapshot(event)` = 00:00 UTC on the day **before** the event,
  capped at ohsome's newest data (live check: 2026-07-27 09:00Z). For Trishuli →
  2026-07-27; for a 2021 flood → the day before that flood. The day-before margin covers
  time zones (00:00 UTC = 05:45 in Nepal). Works for any judge-chosen event, not just 2026.
- **Why osmnx isn't installed at all:** its download functions fetch *current* OSM via
  Overpass (post-event = forbidden). Building the road graph with networkx from our ohsome
  data removes any doubt (approved P15).
- *Judge may ask:* "How can you prove you didn't use EMSR927 as input?" → Pipeline code
  can't import it (test), can't reach it over HTTP (runtime allowlist), and the scanner
  runs on every commit and in CI.

## 7. Secret protection
| Layer | What it does | If removed |
|---|---|---|
| `.gitignore` | `.env`, key files, credentials, cache/outputs/logs, validation data, organizer PDFs never tracked. A test asks **git itself** (`git check-ignore`) | A `git add .` could publish keys |
| gitleaks + detect-private-key (pre-commit) | Block a commit that contains anything key-shaped | Relying on memory alone |
| Fake keys built at runtime in tests | Scanners run with **zero exceptions** | We'd need allowlist entries, which are holes |
| Redacting log formatter | Masks registered secrets + credential patterns, **including inside tracebacks** | A failed API call could print the key into a log or screen recording |
| `SecretStr` + `doctor`/`config-show` showing only "set (hidden)" | Settings can be inspected safely | Debug printing leaks keys |
| CDSE login token kept by the openEO client in the user profile; pipeline only reuses it (`connect()` never prompts) | Nothing login-related ever lives in the repo | A token file in the project folder could be committed |
| `net.py` as the only HTTP client | One choke point: allowlist, timeouts, retries | Scattered requests with no timeout can freeze a demo |

## 8. Code quality and CI
- **ruff** with `S` (bandit) rules: catches hard-coded passwords, unsafe `yaml.load`,
  `pickle`, shell injection patterns. Result on our code: no security findings.
- **pre-commit**: the checks above run automatically before every commit; remote hooks are
  pinned to commit SHAs (a moved tag upstream can't change what runs).
- **GitHub Actions (`.github/workflows/ci.yml`)**:
  - tests on **Ubuntu and Windows**, since judges may use either;
  - full-history gitleaks scan (binary verified by SHA-256);
  - `pip-audit` for known vulnerabilities (local result: none found in runtime or dev deps);
  - read-only token, **no repository secrets at all**, SHA-pinned actions, no credential
    persistence. CI has nothing it could leak.
- **Dependabot**: weekly PRs for outdated/vulnerable dependencies.
- **`.gitattributes`**: LF line endings everywhere, so Windows and Linux see identical files.

## 9. `login`, `doctor` and `check_cdse.py`
- `login`: one-time Copernicus Data Space login (device code: a link + code you approve in
  the browser). The token is stored by the openEO client in your user profile.
- `doctor`: a pre-flight checklist before any live demo: Python, packages, config, `.env`,
  writable folders, disk, CDSE catalogue reachable, CDSE login valid, ohsome reachable, LLM
  key. Secrets are shown only as set/not set. Exit code 1 if anything blocking is wrong.
- `check_cdse.py`: **lists every Sentinel-1 scene around the event grouped by track** (public
  catalogue, no login) and, when logged in, reads the Copernicus DEM at Syabrubesi through
  openEO. This told us *before* writing M1 which tracks have both pre- and post-event images.

## 11. Rework (2026-10-11): why Copernicus Data Space only, no Earth Engine
- **Decision (author):** follow the brief literally. Its dataset table names
  dataspace.copernicus.eu as the source of Sentinel-1/2, and the brief requires running
  "end-to-end from raw satellite data". Earth Engine is not mentioned in the brief, and its
  Sentinel-1 copies are terrain-corrected with SRTM, a DEM that is not an allowed input.
  Using only the named source removes that question entirely.
- **What CDSE gives us:** a public STAC catalogue (scene search, no login) and openEO
  processing on CDSE's own infrastructure: `sar_backscatter` calibrates Sentinel-1 GRD
  with terrain correction using **Copernicus DEM** (`COPERNICUS_30`, an allowed input),
  plus Sentinel-2 L2A and the Copernicus DEM itself.
- **Why `openeo.dataspace.copernicus.eu` and not `openeofed...`:** the federated endpoint
  may run work on partner platforms outside CDSE; the plain endpoint stays on CDSE.
- **How it is enforced:** collection allowlist, endpoint constant, scanner rule that fails
  on any Earth Engine/geemap import or the federation endpoint.
- **Trade-offs (honest):** CDSE processing is slower than Earth Engine, the free tier allows
  2 concurrent requests and has monthly credits, and there is no second provider to fall
  back on. Mitigations: caching, area cap, small requests, clear progress messages,
  pre-computed case study, and a clear message instead of a crash if CDSE is unreachable.
- *Judge may ask:* "Where does your satellite data come from?" → Only from the Copernicus
  Data Space Ecosystem, the source named in the brief, processed with the Copernicus DEM;
  the test suite fails if any other platform is imported.
